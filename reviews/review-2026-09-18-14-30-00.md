### P1 — 严重（逻辑缺陷 / 数据风险）

#### 1. `hasPendingWorkByKindScript` JSON 子串匹配对空格/格式变化脆弱
- **文件**: `/Users/leichujun/Workspaces/rtc-agent/server/pkg/rtc-queue/lua.go:440-473`
- **行号**: 453-454, 464-465
- **严重程度**: P1
- **描述**: Lua 脚本通过 `'"kind":"' .. kind .. '"'` 做简单子串匹配来识别 work item 的 kind。这假设 JSON 序列化格式固定为无空格 `"kind":"submit"`。如果上游 `json.Marshal` 的行为变化（如未来切换为 `json.MarshalIndent`，或字段顺序调整导致 `kind` 前后出现空格），匹配会失败，导致 dedup 判断错误 —— 同一个 session 可能并发执行两个 compact 或两个 submit，引发上下文压缩竞争或重复 LLM 调用。
- **建议修复**: 在 Redis 的 work hash 中增加一个独立的 `kind` 字段，publish 时由 Go 代码写入。Lua 脚本改为 `HGET "work:.." "kind"` 精确匹配。这样完全消除对 JSON 格式的依赖。

### P2 — 中等（潜在风险 / 设计改进）

#### 2. `CheckOrigin` 使用 `EqualFold` 进行大小写不敏感匹配
- **文件**: `/Users/leichujun/Workspaces/rtc-agent/server/internal/server/server.go:293`
- **严重程度**: P2
- **描述**: `strings.EqualFold(allowed, origin)` 允许 `HTTP://EVIL.COM` 匹配 `http://evil.com`。虽然 DNS 本身大小写不敏感，但 Origin header 的 scheme 部分在某些浏览器/代理下可能被保留原样。更关键的是，如果 `AllowOrigins` 配置项本身有拼写错误（如 `http://localhost:3000/` 带尾斜杠 vs 不带），EqualFold 无法发现配置错误。
- **建议修复**: 使用精确匹配（`==`）或先对两边做 URL 规范化后再比较。开发模式保留宽松匹配。

#### 3. `Server.Start` 缺少幂等保护
- **文件**: `/Users/leichujun/Workspaces/rtc-agent/server/internal/server/server.go:97`
- **严重程度**: P2
- **描述**: `Start()` 没有检查是否已经启动。如果误调用两次，会启动两个 worker goroutine、两个 stale scanner、两个 HTTP server，导致 goroutine 泄漏和端口冲突。`lifecycle.Manager` 已实现了幂等保护（`started` bool），Server 应保持一致。
- **建议修复**: 在 `Start()` 入口检查 `s.started`（或类似标志），已启动则返回错误。

#### 4. `loop.reenqueueLoop` 无条件 re-enqueue，缺少活跃状态二次验证
- **文件**: `/Users/leichujun/Workspaces/rtc-agent/server/internal/loop/recovery.go:125-174`
- **严重程度**: P2
- **描述**: `reenqueueLoop` 在重新入队 asynq 任务后更新 `asynq_task_id`，但没有再次验证 loop 仍然是 active 状态。如果在 `FindStaleLoops` 查询和 `EnqueueContext` 之间，loop 被用户取消，会导致一个已取消的 loop 收到新的 asynq 任务。虽然 `HandleLoopTask` 有 `FindActive` 校验（任务会被跳过），但会白白创建一个 asynq 任务，并在 inspector 中留下僵尸记录。
- **建议修复**: 在 `reenqueueLoop` 中，更新 task_id 前再次检查 loop 状态（或使用 CAS 更新 `WHERE status = 'active'`）。

#### 5. `converter.toProtocolMessage` 流式消息 chunk 覆盖逻辑
- **文件**: `/Users/leichujun/Workspaces/rtc-agent/server/internal/updates/update_publisher.go:148-162`
- **严重程度**: P2
- **描述**: 当消息处于 streaming 状态时，代码用 Redis chunks 覆盖 `m.Content`。但如果 `json.Unmarshal` 成功但 `json.Marshal` 失败（罕见但可能），fallback 路径 `m.Content = strings.Join(chunks, "")` 会丢失原始的 ContentData 结构（type 信息）。客户端收到的是一个纯文本字符串而非 ContentData JSON。
- **建议修复**: 在 fallback 路径中，手动构造 ContentData JSON（保留 type 字段）。

#### 8. 关键分布式路径缺少 Prometheus 指标
- **文件**: `/Users/leichujun/Workspaces/rtc-agent/server/internal/loop/worker.go` 全文；`/Users/leichujun/Workspaces/rtc-agent/server/internal/loop/recovery.go` 全文

- **描述**: loop worker 的 `HandleLoopTask` 和 recovery 扫描没有 Prometheus 指标。关键操作（task 处理成功/失败率、recovery 触发次数、re-enqueue 延迟）不可观测。在生产环境中，如果 loop 任务堆积或 recovery 频繁触发，运维无法从 metrics dashboard 发现。

#### 9. `ResumeWorkPriority` 可能与其他高优先级任务冲突
- **文件**: `/Users/leichujun/Workspaces/rtc-agent/server/pkg/rtc-queue/types.go:82`
- **严重程度**: P2
- **描述**: `ResumeWorkPriority = 100` 被注释为"必须始终高于 fresh submit"。但如果未来增加新的高优先级 work kind（如 heartbeat、health check），可能会意外使用相同或更高的 priority，导致 resume 被延迟。rtc-queue 的 priority 是 `score = -priority`（越高越先被 claim），缺少 priority 空间的文档化治理。
- **建议修复**: 在 `types.go` 中添加 priority 空间文档（如 `0=normal, 100=resume, 200=critical-future`），或在 `WorkPayload` 中用常量枚举替代 magic number。

#### 10. `NewUpdatePublisher` 函数过长（78 行）
- **文件**: `/Users/leichujun/Workspaces/rtc-agent/server/internal/updates/update_publisher.go:95-172`
- **严重程度**: P2
- **描述**: `NewUpdatePublisher` 函数体 78 行，包含 4 个 resolver 的注册逻辑。每个 resolver 是一个闭包，逻辑复杂度不同（Session resolver 有 token estimate 计算，Message resolver 有 streaming chunk 拼接）。函数过长降低可读性。
- **建议修复**: 将每个 resolver 提取为独立的 `newXxxResolver()` 工厂函数。

#### 11. `publishScript` 硬编码 Redis key 前缀
- **文件**: `/Users/leichujun/Workspaces/rtc-agent/server/pkg/rtc-queue/lua.go:111-126`（以及 `completeScript`, `cancelScript` 等多个脚本）
- **严重程度**: P2
- **描述**: Lua 脚本内部使用硬编码的 `"session:lock:"`, `"queue:session:"`, `"work:"` 前缀，而 Go 层通过 `keyLock()`, `keyQueue()`, `keyWork()` 函数生成 key。如果未来修改 key 前缀，Go 层会自动适配，但 Lua 脚本中的硬编码字符串不会同步更新，导致运行时错误。
- **建议修复**: 将所有在 Lua 脚本中构造的 key 作为 KEYS[] 参数从 Go 层传入，消除 Lua 脚本中的硬编码前缀。这是 Redis Lua 脚本的最佳实践。

#### 15. `pricing.go` — `calculateCostMicros` 缺少负值保护

#### 16. `lifecycle.Manager.Stop` — `shutdownOnce.Do` 后 wg.Wait 可能永久阻塞
- **文件**: `/Users/leichujun/Workspaces/rtc-agent/server/internal/lifecycle/manager.go:109-164`
- **严重程度**: P3
- **描述**: 如果 `Go()` 启动的某个 goroutine 没有监听 `m.ctx.Done()`（编程错误），`m.wg.Wait()` 会永久阻塞，`Stop()` 只能在 `ctx.Done()` 时返回。此时 `ctx.Err()` 被返回，但 goroutine 仍然在后台运行（leaked）。
- **建议修复**: 在 `Go()` 方法文档中强调 goroutine 必须响应 ctx 取消。可考虑在 `Stop()` 超时后记录 leaked goroutine 的 stack trace。

#### 17. `lua.go` — `cancelScript` 中 `KEYS[1]:sub(6)` 硬编码偏移
- **文件**: `/Users/leichujun/Workspaces/rtc-agent/server/pkg/rtc-queue/lua.go:188`

- **建议修复**: 同 P2 #11 — 将 work_id 作为 ARGV 参数传入。

#### 19. `throttle.go` — `Stop()` 后 `Do()` 可能 panic
