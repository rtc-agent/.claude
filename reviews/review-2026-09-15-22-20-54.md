## 特别关注分析

### 1. 竞态条件: FailTurn 和 Publish 之间是否有时间窗口？

**结论: 无竞态风险。**

分析:
- FailTurn 将 Turn 状态设为 "failed"，session 状态设为 "idle"
- Publish 将新 work item 入队
- 新 Process 调用 CreateTurn 创建新 Turn，BeginTurn 将 session 设为 "running"
- 由于 rtc-queue 的 session lock 机制，同一 session 不会有两个并发 Process
- mgr.Cleanup() 已在 reactive compact 分支之前执行，session lock 已释放
- 新 worker 获取 lock → 创建新 manager → 正常流程

### 2. cleanup 冲突: Process() return 后新 Turn 是否会与 Cleanup 冲突？

**结论: 无冲突。**

分析:
- `mgr.Cleanup()` 在 line 250 执行，在 reactive compact 分支（line 317-367）之前
- Cleanup 会: CompleteAll() → 停止 lock renewal → 释放 session lock → notify workers
- 新 Process 会通过 GetOrCreate 创建全新的 SessionTurnManager
- Checkpoint key 基于 sessionID（非 turnID），新 Turn 会复用/覆盖旧 checkpoint — 这是预期行为

### 3. work 记账: queue.Publish 的 work item 是否能正确被 Worker 消费？

**结论: 能正确消费。**

分析:
- Publish 的参数: `sessionID`, `MarshalSubmitPayload(p.SessionID, attempt)`, `priority=100`
- MarshalSubmitPayload 生成 `{"kind":"submit","session_id":"..."}` — 标准 submit work payload
- Priority 100 与正常 submit 一致
- rtc-queue Worker 会 pick up → 调用 Agent.Process → CreateTurn → BeginTurn → 正常运行

## 遗留问题

1. **[警告] FailTurn 后 session 状态短暂变为 "idle"**: reactive compact 路径中 FailTurn 将 session 设为 "idle"，新 Process 的 BeginTurn 再设为 "running"。前端可能观察到 session 状态闪烁（running → idle → running）。建议评估是否需要在 reactive compact 路径中使用特殊的 session 状态（如 "compacting"）或跳过 session 状态更新。

2. **[建议] InsertFeedbackMessage wrapper 静默丢弃 uuid.Parse 错误**: `agent.go:346-347` 中 `uuid.Parse` 的错误被丢弃。虽然上游保证了 sessionID/turnID 的合法性，但建议添加 parse error 的日志记录以提高可观测性。

3. **[建议] MarshalSubmitPayload 的 attempt 参数未使用**: `error_types.go:31` 中 `_ = attempt` 明确表示保留但未使用。建议在代码稳定后清理此参数，或在 payload 中实际记录 attempt 以供 metrics/tracing 使用。

4. **[建议] Reactive compact 循环中 InsertFeedbackMessage 可能重复: 如果 attempt 1 压缩成功但 Publish 失败，attempt 2 会再次插入 "compressing" 消息。建议在 Publish 失败后 break 前考虑标记已插入消息，或在后续 attempt 中跳过重复插入。**
