### 7. 分布式系统风险

**发现的问题**: 无

**审查要点**:

#### 7.1 atomic 操作正确性 ✅

- **compressionThreshold** (`atomic.Int64`): 正确使用 `Store()`/`Load()`，替代了原来的 `int64` 字段。
- **globalTokenCounter** (`atomic.Value` + `tokenCounterHolder`): wrapper 模式正确解决了 `atomic.Value` 存储不同类型会 panic 的问题。`init()` 中初始化了默认值，避免首次 `Load()` 返回 nil。
- **debugMode** (`atomic.Bool`): 正确使用 `Store(true)`/`Load()`，所有 15 处读取都已替换为 `IsDebugMode()`。
- **lockLost** (`atomic.Bool`): 正确使用，与 `consecutiveRenewFailures` (`atomic.Int64`) 配合实现三层防御。

#### 7.2 锁粒度优化 ✅

- **GetOrCreate** (`session_registry.go`): 读锁快速路径 → 无锁 Redis 操作 → 写锁 double-check 模式正确。double-check 防止了 TOCTOU 竞态。
- **TopicBroker.Subscribe** (`topic_broker.go`): 锁内只做检查和保存引用，锁外执行 Redis 操作。存在微小的 TOCTOU（两个并发 Subscribe 可能对同一 channel 发送两次 Redis SUBSCRIBE），但 Redis SUBSCRIBE 是幂等的，不影响正确性，只是轻微的效率损失。这是合理的权衡。

#### 7.3 lockLost 容错 ✅

- **maxConsecutiveRenewFailures = 3**: 合理的阈值。瞬态 Redis 错误（网络抖动、连接池耗尽）不会立即触发 lockLost，只有连续 3 次失败才标记。
- **计数器重置**: 成功响应时 `consecutiveRenewFailures.Store(0)` 正确重置。
- **明确锁丢失**: `ok == false`（Redis 成功响应但锁已丢失）立即标记 lockLost，不经过计数器，这是正确的。

#### 7.4 ReplaceAndCreate TOCTOU ✅

- `session_registry.go` 的 `Replace` 方法在等待 `oldDone` 后重新获取写锁并 double-check `r.managers[sessionID]`，防止并发创建。模式正确。

**总体评价**: 并发模式设计合理，double-check 防止了 TOCTOU，锁粒度优化避免了长时间持锁导致的性能问题。

### 3.5 GetOrCreate 锁粒度优化 [Medium] ✅

**文件**: `pkg/turn-agent/session_registry.go`

**修改**: 读锁快速路径 → 无锁 Redis → 写锁 double-check

**评审**:
- 读锁快速路径：`r.mu.RLock()` → 检查 `r.managers[sessionID]` → `r.mu.RUnlock()`
- 无锁 Redis：`queue.ClaimWithCredential` 在无锁状态下执行
- 写锁 double-check：`r.mu.Lock()` → 再次检查 `r.managers[sessionID]` → 创建 → `r.mu.Unlock()`
- double-check 防止了 TOCTOU 竞态

**结论**: 修复正确。模式与经典的 double-checked locking 一致。

### 3.6 TopicBroker.Subscribe 锁粒度优化 [Medium] ✅

**文件**: `pkg/centrifuge-plus/topic_broker.go`

**修改**: 锁内只做检查和保存引用，锁外执行 Redis 操作

**评审**:
- 锁内：检查 `subscribedChans`，保存 `pubSubClient` 引用
- 锁外：执行 Redis `SUBSCRIBE` 命令
- 重新获取锁：更新 `subscribedChans`

**潜在的微小 TOCTOU**: 两个并发 `Subscribe` 可能对同一 channel 发送两次 Redis SUBSCRIBE。但 Redis SUBSCRIBE 在同一连接上是幂等的，不影响正确性。

**结论**: 修复正确。这是合理的性能优化，微小的重复 SUBSCRIBE 是可以接受的权衡。

### 3.8 lockLost 瞬态错误误判 [High] ✅

**文件**: `pkg/turn-agent/session_manager.go`

**修改**: 连续 3 次失败才标记 lockLost

**评审**:
- `maxConsecutiveRenewFailures = 3` 常量定义合理

- 失败时递增：`mgr.consecutiveRenewFailures.Add(1)`
- 达到阈值时标记：`if failures >= maxConsecutiveRenewFailures { mgr.lockLost.Store(true) }`
- 成功时重置：`mgr.consecutiveRenewFailures.Store(0)`
- 明确锁丢失（`ok == false`）立即标记，不经过计数器

**结论**: 修复正确。三层防御机制设计合理：
1. 瞬态错误容忍（连续 3 次）
2. 明确锁丢失立即响应
3. lockLost 标记防止 cleanup 误删其他 worker 的锁
