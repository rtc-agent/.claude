## 代码修复

### P1 Bug: Worker 锁续期缺少连续失败计数器

**文件**: `server/pkg/rtc-queue/worker.go` — `processWorkInternal()` 锁续期 goroutine

**问题**:
Worker 层的锁续期逻辑对网络错误和锁丢失（`!ok`）采用不同处理：
- `!ok` → 设置 `lockLost=true`，取消工作
- 网络错误 → 仅调用 `OnError` 记录日志，**不设置 lockLost**，继续处理

这与 SessionTurnManager（`session_manager.go:runLockRenewal`）的连续失败计数器机制不一致。在 Redis 瞬态网络故障场景下，Worker 可能在锁 TTL 过期后仍继续处理同一 Session，导致 split-brain（两个 Worker 同时处理同一 Session）。

**修复**:
在 Worker 的锁续期 goroutine 中添加 `consecutiveRenewFailures` 计数器（阈值 3），与 SessionTurnManager 保持一致：
- 网络错误 → 递增计数器，记录 Warn 日志
- 连续 3 次失败 → 设置 `lockLost=true`，取消工作
- 成功续期 → 重置计数器

**总体评价**: 优秀。三层架构（`internal/agent` 业务逻辑 → `pkg/turn-agent` Turn 管理 → `pkg/rtc-queue` 队列基础设施）清晰，Wire 依赖注入规范。

这次审查中，最引人注目的发现是 Worker 锁续期的 split-brain 风险——一个看似微小的差异（缺少连续失败计数器），却可能在分布式环境下引发两个 Worker 同时处理同一 Session 的严重后果。这正应了那句话：分布式系统中，每一个"不太可能"的假设，都可能是灾难的起点。

修复后的 Worker 与 SessionTurnManager 形成了双层防护——即使一层失守，另一层仍能守住一致性边界。这正是防御性编程的精髓：不信任任何单一组件，用冗余换取安全。
