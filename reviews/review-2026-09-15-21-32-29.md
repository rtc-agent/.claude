**问题 #1 [严重] classifyError 代码示例：Type() 比较方式不精确**

- **位置**: 报告 2.3.1，第 276-294 行
- **现象**: 代码示例中使用 `apiErr.Type() == "overloaded_error"` 进行比较
- **实际代码**: `Type()` 返回 `shared.ErrorType` (即 `type ErrorType string`)
- **影响**: Go 允许命名字符串类型与无类型字符串常量比较，因此代码**可以编译**。但这不是最佳实践——使用 SDK 提供的常量更安全、可维护
- **修复建议**:
```go
// 修复前
case "overloaded_error":
    return ErrorCategoryAPI

// 修复后
case shared.ErrorTypeOverloadedError:
    return ErrorCategoryAPI
```
- **严重程度**: 警告 (代码可运行，但风格不佳，且若 SDK 改变底层表示会断裂)

---

**问题 #3 [严重] classifyError 代码示例：anthropic.Error 的检测方式**

- **位置**: 报告 2.3.1，第 274 行
- **现象**: 代码使用 `var apiErr *anthropic.Error`，但 import 的是 `"github.com/anthropics/anthropic-sdk-go"`
- **实际代码**: `anthropic.Error` 确实是 `apierror.Error` 的类型别名 (`aliases.go:17`)，所以 `*anthropic.Error` 是正确的
- **但是**: 报告正文 2.1.1 节标题为 "Anthropic SDK 错误"，引用的位置是 `internal/apierror/apierror.go`，容易让实施者混淆应该用 `anthropic.Error` 还是 `apierror.Error`
- **修复建议**: 在 2.1.1 节补充说明：
  > `anthropic.Error` 是 `internal/apierror.Error` 的公开类型别名 (见 `aliases.go:17`)。实施时应使用 `anthropic.Error`（来自根包），而非内部包的 `apierror.Error`。
- **严重程度**: 警告 (代码正确，但文档说明不够清晰)

**问题 #4 [中等] 错误映射表：InterruptError 类型混淆**

- **位置**: 报告 2.2 映射表，第 231 行
- **现象**: 映射表中写了 `*compose.interruptError`，检测方法为 `compose.ExtractInterruptInfo(err)`
- **实际情况**:
  - `compose.interruptError` 是**未导出**的类型 (小写 i，`compose/interrupt.go:314`)
  - `adk.InterruptError` 是**已导出**的类型 (大写 I，`adk/turn_loop.go:780`)
  - 实际代码 `session_manager.go:731` 使用的是 `*adk.InterruptError`
  - `compose.ExtractInterruptInfo()` 检测的是 `compose.interruptError` 和 `compose.subGraphInterruptError` (均为未导出类型)
- **影响**: 实施者可能会混淆两种 InterruptError。`adk.InterruptError` 和 `compose.interruptError` 是**不同的类型**，前者是 ADK 层的中断信号，后者是 Compose 层的中断信号
- **修复建议**: 在映射表中拆分为两行：

| 错误场景 | Eino 错误类型 | 检测方法 | ErrorCategory |
|---------|-------------|---------|--------------|
| Agent 中断 (ADK 层) | `*adk.InterruptError` | `errors.As(err, &interruptErr)` | `interrupt` |
| Graph 中断 (Compose 层) | `compose.interruptError` (未导出) | `compose.ExtractInterruptInfo(err)` | `interrupt` |

并在 classifyError 中同时处理两种情况。

- **严重程度**: 警告 (可能导致实施者遗漏 `adk.InterruptError` 的检测)

- **严重程度**: 警告 (不常见但可能发生的边界情况)

**问题 #6 [建议] classifyError 代码示例：getRetryDelay 中的位移运算可能溢出**

- **位置**: 报告 2.3.1，第 370-388 行
- **现象**: `time.Duration(1<<uint(attempt)) * time.Second`
- **影响**: 当 `attempt >= 63` 时，`1<<uint(attempt)` 在 64 位系统上会溢出。虽然实际使用中 attempt 不会这么大（因为有 max 30s 的限制），但代码存在理论上的溢出风险
- **修复建议**: 添加防御性检查:
```go
func getRetryDelay(err error, attempt int) time.Duration {
    if attempt < 0 {
        attempt = 0
    }
    if attempt > 10 { // 硬上限，防止溢出
        attempt = 10
    }
    // ... 其余逻辑
}
```
- **严重程度**: 建议 (实际不会触发，但防御性编程更佳)

### 5. 代码质量

#### 5.1 方案 C 的合理性评估

**结论**: 方案 C 是正确选择。

**验证过程**:
1. 确认 `AsyncIterator` 确实没有暴露 `Close()` 方法 (utils.go:31-37 仅有 `Next()`)
2. 确认底层 `UnboundedChan` 有 `Close()` 但不可访问 (internal 包)
3. 确认 `AsyncGenerator` 有 `Close()`，但它是生产端，消费者无法调用
4. 确认使用反射/unsafe 访问 `ch *internal.UnboundedChan[T]` 会破坏封装，且 `internal` 包在 Go 中有特殊的导入限制

**替代方案评估**: 报告没有充分讨论的一个选项是——在 `consumeStream` 中通过 `stream.Close()` 关闭 StreamReader 来间接让上游的 `AsyncGenerator.Close()` 被调用。但查看源码 `cancel.go:1019-1090`，StreamReader 的 Close 和 AsyncGenerator 的 Close 是独立的，关闭 StreamReader 不会自动关闭 AsyncGenerator。因此方案 C 确实是唯一合理的选择。

#### 5.2 错误 Wrapping 链路验证

**报告描述**: `Anthropic API error -> eino-ext/claude ChatModel.Stream() -> compose internalError -> AgentEvent.Err -> classifyError`

**验证结果**: 
- `compose/error.go:54-60` 中 `newGraphRunError` 确认会包装为 `*internalError`
- `compose/error.go:62-77` 中 `wrapGraphNodeError` 确认会包装为 `*internalError`
- `internalError.Unwrap()` 返回 `origError` (error.go:109-111)
- `errors.As()` 可以穿透 `Unwrap()` 链

**结论**: 报告描述的 wrapping 链路准确。
