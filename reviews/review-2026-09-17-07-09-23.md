## 遗留问题

4 个 dupl 问题无法修复：

1. **query_list.go 内部重复** (2 issues): RtcList 和 TurnList 函数体高度相似。Go 泛型无法轻松抽象不同的 protobuf Request/Response 类型对，除非引入 reflection 或 code generation，这会损害类型安全和可读性。

2. **servicecontext.go 结构性重复** (2 issues): ServiceContext struct 定义和 NewServiceContextWithDeps 构造函数参数列表天然相似，因为都列举了相同的依赖。这是 Go DI 模式的固有特征。

## 诗人寄语

代码如弓，张弛有度。三十一处重复化为四处，非是力有不逮，而是知止而后安。

泛型之美，在于以一御万。四个 helper 函数如四根支柱，撑起了 repo 层的整洁大厦。然而真正的智慧不在于消除一切重复，而在于辨别哪些重复值得保留。struct 与 constructor 的镜像之美，是两个 handler 函数的手足之情——这些不是瑕疵，而是结构的自然纹理。

配置之修，尤胜于代码之改。一个静默失效的 lint 配置，比三十个 lint 问题更危险。修复它，就是修复了团队的眼睛。

前行吧，代码的诗人。完美不在终点，而在每一步的推敲之中。
