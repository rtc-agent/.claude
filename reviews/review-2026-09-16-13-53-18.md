### 6. 错误处理

**发现的问题**: 3 个未受保护的 goroutine（详见下文）

**修复项**:

#### P0: token_callback.go — OnEndWithStreamOutput goroutine 无 panic recovery

- **文件**: `server/internal/agent/token_callback.go:78`
- **严重程度**: 严重
- **问题**: `go func()` 启动的 drain goroutine 没有 `defer recover()`。如果 `drainStreamAndReport` 内部发生 panic（尽管有内部 recover，但不能完全排除所有边界情况），将导致整个进程崩溃。
- **修复说明**: 添加 `defer recover()` 包装，使用 `logger.Error` 记录 panic 信息和 stack trace。

```go
// 修复前
go func() {
    defer cancel()
    h.drainStreamAndReport(bgCtx, output)
}()

// 修复后
go func() {
    defer cancel()
    defer func() {
        if r := recover(); r != nil {
            logger.Error(bgCtx, "drainStreamAndReport panic",
                zap.Any("recover", r),
                zap.String("stack", string(debug.Stack())))
        }
    }()
    h.drainStreamAndReport(bgCtx, output)
}()
```

#### P1: worker.go — Stop() 中的 wait goroutine 无 panic recovery

- **文件**: `server/pkg/rtc-queue/worker.go:200`
- **严重程度**: 严重
- **问题**: `go func() { w.wg.Wait(); close(done) }()` 没有 `defer recover()`。虽然 `wg.Wait()` 极少 panic，但根据并发规范的铁律："如果你写了 `go func()`，那个 func 里就应该有 `defer recover()`"。
- **修复说明**: 添加 `defer recover()` 包装，通过 `w.logError` 记录。

```go
// 修复后
go func() {
    defer func() {
        if r := recover(); r != nil {
            w.logError("stop wait panic",
                "recover", r, "stack", string(debug.Stack()))
        }
    }()
    w.wg.Wait()
    close(done)
}()
```

#### P2: lifecycle/manager.go — Stop() 中的 wait goroutine 无 panic recovery

- **文件**: `server/internal/lifecycle/manager.go:135`
- **严重程度**: 严重
- **问题**: 与 P1 完全相同的模式：`go func() { m.wg.Wait(); close(done) }()` 没有 panic recovery。
- **修复说明**: 添加 `defer recover()` 包装和 `runtime/debug` 导入。

```go
// 修复后
go func() {
    defer func() {
        if r := recover(); r != nil {
            logger.Error(context.Background(), "[lifecycle.Manager] shutdown wait panic",
                zap.Any("recover", r),
                zap.String("stack", string(debug.Stack())))
        }
    }()
    m.wg.Wait()
    close(done)
}()
```

**总体评价**: 错误处理整体优秀。错误包装使用 `%w` 保留错误链，每个层次附加有意义的上下文。自定义错误类型（如 `StreamIdleTimeoutError`）设计合理，支持 `errors.Is` 类型判断。
