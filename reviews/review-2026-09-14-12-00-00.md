## 已修复的问题

### Fix 1: 导出循环缺少 context 取消检查 [中等]

**文件**: `server/pkg/memory/exporter.go:165-180`

**问题**: `Export` 方法的概念文档写入循环未检查 `ctx.Err()`。当客户端在大数据量导出过程中断开连接时，服务端仍会继续处理所有剩余 memory，浪费 CPU 和内存资源。

**修复**: 在每次循环迭代开始时检查 `ctx.Err()`，若 context 已取消则提前返回。

```go
for _, m := range memories {
    if err := ctx.Err(); err != nil {
        return fmt.Errorf("export cancelled: %w", err)
    }
    // ... write concept doc
}
```

### Fix 2: HTTP 请求体缺少大小限制 [中等]

**文件**: `server/internal/handler/http/memories.go:59-60`

**问题**: `json.NewDecoder(r.Body).Decode(&req)` 未限制请求体大小。恶意客户端可发送超大 JSON payload 导致 OOM。

**修复**: 使用 `http.MaxBytesReader` 限制请求体为 1 MB。

```go
r.Body = http.MaxBytesReader(w, r.Body, 1<<20)
```

### Fix 3: Content-Disposition 文件名过于静态 [中等]

**文件**: `server/internal/handler/http/memories.go:102-104`

**问题**: 原始文件名固定为 `memories.tar.gz`，不区分 scope 和时间，不利于用户管理多个导出文件。

**修复**: 动态生成包含 scope 和时间戳的文件名。

```go
filename := fmt.Sprintf("memories-%s-%s.tar.gz", req.Scope, time.Now().Format("20060102-150405"))
```

### Fix 4: IncludeLinks 字段文档化 [轻微]

**文件**: `server/pkg/memory/exporter.go:24`

**问题**: `ExportOptions.IncludeLinks` 被接受但从未使用，属于死代码。

**修复**: 添加注释标记为 `reserved: include cross-reference links between concept docs`，明确其预留状态。

**发现的问题**:

- **导出失败后的响应处理** - `memories.go:118-124` - **严重程度**: 建议
  - 一旦 Content-Type/Content-Disposition 头已写入（line 102-104），Export 失败时无法再返回错误 JSON。
    代码中已有注释说明这一点。这是一个已知的 HTTP 流式响应限制，当前处理方式（记录日志）是合理的。
  - **建议**: 可考虑先写入缓冲区，确认 Export 成功后再写响应头。但这会牺牲流式传输的内存效率。
    对于当前规模，保持现状即可。

  - 由于类型数量有上界（9），这不是严重问题。若未来类型扩展，可考虑批量查询优化。

- **全量加载到内存** - `exporter.go:125-128` - **严重程度**: 建议

    对于极大数据量（数万条 memories），可能导致内存峰值较高。
  - **建议**: 未来可改为流式查询 + 流式写入 tar，但当前阶段无必要。
