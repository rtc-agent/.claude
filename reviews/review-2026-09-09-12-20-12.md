## TurnID 不匹配 Bug 调查结论

### Bug 确认

**确认存在竞态条件 bug**。

### 根因分析

`runPumpLoop` 使用 `select` 监听 `ctx.Done()` 和 notification channel。Go 的 `select` 在多个 case 同时就绪时随机选择一个执行。这意味着当 `ctx` 被取消时，如果恰好有 notification 到达，pump loop 可能选择读取 notification 而不是退出。

#### 竞态时序

```
Server-1 (Turn 1 完成):
  1. TurnLoop 退出 (agent 完成)
  2. Monitor goroutine 调用 Stop()
  3. Stop() 调用 pumpCancel()  <-- ctx 取消
  4. Stop() 等待 pumpDone...
  5. (等待 pump goroutine 退出)
  6. ReleaseSession()           <-- 释放锁

Pump goroutine (仍在运行):
  select {
  case <-ctx.Done():            <-- 就绪
  case msg := <-ch:             <-- 同时就绪 (新 notification 到达)
  }
  如果 select 选择 ch:
    → 通过 session filter (msg.Payload == ta.sessionID)
    → ClaimWithCredential (credential 仍有效，因为锁还未释放)
    → LoadWork → 拿到 Turn 2 的 work
    → Push 到 TurnLoop (带着 Turn 1 的 turnID!)
```

此时 Turn 2 的 work 被错误地推入了 Turn 1 的（已停止的）TurnLoop。Turn 2 的 Process 调用 `CreateTurn` 生成了 turnID `4561`，但 pump loop 推送的 work item 携带的 turnID 是 `14a1`（Turn 1 的 ID）。

### 修复方案

在 session filter 通过之后、claim 操作之前，添加 `ctx.Err()` 检查：

```go
if ctx.Err() != nil {
    return
}
```

这将 pump loop 的退出点从"select 的 ctx.Done() case"前移到"处理 notification 的同步路径"上。由于 Go 的单 goroutine 内指令是顺序执行的，ctx 取消后 `ctx.Err()` 必然返回非 nil，pump loop 不会再执行 claim。

### 残余风险评估

`ctx.Err()` 检查与 `ClaimWithCredential` 之间仍存在极小的理论窗口（1-2 条 CPU 指令）。但在实践中：
1. 该窗口在 nanosecond 级别，而 notification 到达是 microsecond 级别的事件
2. 即使极小概率命中，session lock TTL 提供了最终安全网——锁会在 120s 后过期，work 会被重新调度
3. 要彻底消除该窗口需要引入更重的同步机制（如 mutex 或 wait group），但会显著增加复杂度，收益不成比例

结论：当前修复在实用性和正确性之间取得了合理平衡。
