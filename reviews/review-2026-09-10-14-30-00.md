## 详细审查结果

### 1. 消息顺序

**发现的问题**:

- **Summary 展开后所有消息共享同一 CreatedAt** - `data_context.go:244-253`
  - **严重程度**: 建议
  - **修复状态**: 未修复（设计决策，风险可控）
  - **修复说明**: `buildMessagesFromSummaryItems` 将所有 SummaryItem 的 CreatedAt 设为 summary 消息的时间戳。这会导致 microcompact 的 `findLastAssistantTime` 在 summary 位于开头时返回该时间戳，但由于 microcompact 只清理旧 tool result 而 summary 不含 tool result，实际影响有限。保留原设计，避免引入不确定的 CreatedAt 排序。

- **Attachment 注入顺序反转** - `attachment.go:172-174`
  - **严重程度**: 严重
  - **修复状态**: 已修复
  - **修复说明**: `BuildAttachments` 中每个 attachment 通过 `append([]*Message{...}, messages...)` 前置到列表头部，导致最终顺序与配置顺序完全相反。配置的优先级为 TodoList > SessionMemory > UserMemory，实际注入顺序变为 UserMemory > SessionMemory > TodoList。修复方式：改为先收集到 `collected` 切片中保持顺序，不再逐个前置。

**总体评价**: Summary 截断逻辑正确（从尾部向前扫描找到最近的 summary，按 GlobalOffset 排序恢复顺序）。GenInput 通过 `toEinoMessages` 保序传递，GenResume 不重新加载消息（依赖 checkpoint 状态），两者均正确。

### 2. 上下文注入

**发现的问题**:

- **Attachment 截断后 original_tokens 日志不准确** - `attachment.go:149`
  - **严重程度**: 警告
  - **修复状态**: 已修复
  - **修复说明**: 原代码在截断后调用 `estimateStringTokens(content)` 计算 "original_tokens"，此时 content 已被截断，返回值等于 truncated_tokens，日志中的 original_tokens 字段失去意义。修复方式：在截断前保存原始 token 数。

- **Attachment 注入时机正确** - `data_context.go:91-109`
  - **严重程度**: 无问题
  - **修复状态**: 无需修复
  - **说明**: Attachment 在 tool result budget 和 microcompact 之后注入，在 command prompt 注入之前。这个顺序合理：先压缩历史，再注入动态上下文，最后注入命令提示。

**总体评价**: Attachment 管理器设计合理（token 预算、优先级、截断策略），但注入实现存在顺序反转 bug。

### 3. 空内容处理

**发现的问题**:

- **convertDBMessage 返回 nil 导致消息列表包含 nil 条目** - `data_context.go:72-75`
  - **严重程度**: 严重
  - **修复状态**: 已修复
  - **修复说明**: 当 `convertDBMessage` 因内容解析失败或未知类型返回 nil 时，原代码通过 `append(messages, converted...)` 将 nil 直接追加到消息列表。nil 消息传播到 `toEinoMessage` 返回 nil `*schema.Message`，可能导致下游 nil 指针崩溃。修复方式：在 loadMessages 中过滤 nil 条目；同时在 `mergeAssistantMessages` 中增加 nil 防御。

- **mergeAssistantMessages 对 nil 条目无防御** - `data_context.go:287-300`
  - **严重程度**: 严重（测试中发现）
  - **修复状态**: 已修复
  - **修复说明**: 当输入切片包含 nil 时，`msg.Role` 访问触发 nil 指针崩溃。新增 nil 检查，跳过 nil 条目。

- **Thinking-only 消息后跟非 assistant 消息产生空内容块** - `data_context.go:305-316`
  - **严重程度**: 警告
  - **修复状态**: 已修复
  - **修复说明**: 原代码在 thinking-only 消息后无 assistant 消息时，一律将 ReasoningContent 转为 Content。当后续消息是 tool result 时，这会产生 `assistant{text:""}` 空内容块（Claude adapter 不识别 ReasoningContent，fallback 生成空 text block），且 `assistant{text}` 位于 `tool{result}` 之前违反 Claude API 的 tool call 配对契约。修复方式：后续为非 assistant 消息时直接丢弃 thinking（推理隐含在 tool call 参数中）；仅当 thinking 是最后一条消息时才转为 text。

**总体评价**: 空内容处理经过多轮修复已趋于健壮。`mergeAssistantMessages` 的三路分支（合并/丢弃/转换）覆盖了所有边界情况。

### 4. Tool Calling 配对

**发现的问题**:

- **tool_call_id 一致性验证通过** - `tools.go:249-250`, `submitrtcresult.go:173`
  - **严重程度**: 无问题
  - **修复状态**: 无需修复
  - **说明**: toolcall_input 使用 eino 注入的 `compose.GetToolCallID(ctx)` 作为 Id，toolcall_output 显式复制 `inputToolCall.Id`（`Id: inputToolCall.Id // 与 toolcall_input 保持一致的 tool_call_id`）。两者保持一致，配对正确。

- **convertDBMessage 中 tool call 配对转换正确** - `data_context.go:177-205`
  - **严重程度**: 无问题
  - **修复状态**: 无需修复
  - **说明**: toolcall_input 转换为 `assistant{ToolCalls: [{ID: toolCall.Id}]}`，toolcall_output 转换为 `tool{ToolCallID: toolCall.Id}`。ID 来源相同，配对正确。

- **Microcompact 保留 ToolCallID 元数据** - `microcompact.go:106-111`
  - **严重程度**: 无问题
  - **修复状态**: 无需修复
  - **说明**: 即使 tool result 内容被清除，ToolCallID 和 ToolName 元数据均被保留，不会破坏配对关系。

**总体评价**: Tool call 配对机制设计严谨，从 ID 生成（eino framework）、持久化（DB）、到重新加载（convertDBMessage）全链路一致。

### 5. 其他维度

- Resume work item 进入 GenInput 时有诊断日志（`gen_input.resume_work_fallback`），便于排查 checkpoint 丢失问题

**可观测性**:

- 关键路径均有结构化日志（`logIfEnabled`），包含 session_id、turn_id 等关键字段
- Attachment 构建记录了耗时和 token 数
- Token usage 通过 callback 机制记录

## 诗人寄语

上下文管理是 LLM Agent 的生命线。消息如同河流中的水滴——每一滴都承载着对话的记忆，每一次转折都需要精准的引导。

此次审查发现了一个隐蔽的顺序反转 bug：attachment 在注入时像叠纸牌一样逐个前置，最终呈现的顺序与设计意图完全相反。这类 bug 的可怕之处在于它不会崩溃、不会报错，只是悄悄改变行为的语义——直到某天 LLM 因为上下文的优先级错位而给出令人困惑的回答。

另一个亮点是测试驱动的发现：为 nil 安全添加的测试直接暴露了 `mergeAssistantMessages` 的 nil 指针崩溃。这再次证明——测试不仅是验证工具，更是探索工具。当你为边界情况写下测试时，代码会在你面前展示自己的脆弱。

代码如诗，字字珠玑。愿每一次 review 都让这首诗更加精炼。
