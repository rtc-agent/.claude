## 执行摘要

发现了 1 个严重缺陷（Redis Pub/Sub 竞态条件导致 cancel 信号丢失）和 2 个贡献性缺陷（操作顺序错误、cancel 状态未持久化）。全部 3 个问题均已修复，形成三层防护的 cancel 信号传递链路。代码已通过 `go build` 编译验证。

## 根因分析

### 完整 cancel 信号链路（修复后）

```
StopTurn RPC
  │
  ├─► CancelSession (Redis)
  │     │
  │     └─► cancelSessionActiveScript (Lua, 原子操作)
  │           │
  │           ├─► 1. HSET work:status = "cancelled"  ← [Fix 2a: 新增] 持久化状态
  │           ├─► 2. PUBLISH session:cancel:<sid>     ← fire-and-forget
  │           └─► 3. DEL session:lock:<sid>
  │
  ├─► Worker (processWorkInternal)
  │     │
  │     ├─► [Fix 2b: Safety-net #1] LoadWork 后检查 work.Status
  │     │     └─► 若 status == "cancelled" → 立即触发 cancel
  │     │
  │     ├─► SubscribeCancel (订阅 Redis Pub/Sub)
  │     │
  │     ├─► [Fix 2c: Safety-net #2] SubscribeCancel 后重新检查 work.Status
  │     │     └─► 若 status == "cancelled" && 未处理 → 立即触发 cancel
  │     │
  │     └─► Cancel listener goroutine
  │           └─► 收到 CancelMessage → cancelCh ← cm
  │
  └─► Agent.Process (turn-agent)
        │
        └─► Cancel listener goroutine
              │
              ├─► mgr.Loop().Stop(adk.WithImmediate())
              │     └─► eino TurnLoop: cancelContext.sendImmediateInterrupt()
              │           ├─► 中断 compose graph 执行
              │           └─► 关闭 immediateChan
              │
              ├─► turnCancel()  ← 取消 turnCtx
              │
              └─► wrapStreamWithCancelMonitoring (eino 内部)
                    └─► 检测到 immediateChan 关闭
                          └─► 注入 ErrStreamCanceled → LLM HTTP 流中断
```

### 竞态窗口分析（修复前）

**竞态窗口 1: CancelSession → LoadWork 之前**
- CancelSession 在 worker 执行 ClaimWithCredential 之后、LoadWork 之前运行
- Pub/Sub 消息被发送，但 worker 尚未订阅 → 消息丢失
- **修复**: Safety-net #1 — LoadWork 返回后检查 work.Status（依赖 Fix 2a 持久化的状态）

**竞态窗口 2: LoadWork → SubscribeCancel 之间**
- CancelSession 在 worker 执行 LoadWork（返回 "processing"）之后、SubscribeCancel 之前运行
- Pub/Sub 消息被发送，但 worker 尚未订阅 → 消息丢失
- **修复**: Safety-net #2 — SubscribeCancel 后重新检查 work.Status

**操作顺序问题**
- 旧代码先更新 DB（turn.status = cancelled），再发送 cancel 信号
- 前端看到 turn 已取消，但 LLM 仍在输出 → 用户体验矛盾
- **修复**: [Fix 1] 调换顺序 — 先发 cancel 信号，再更新 DB

### 6. 错误处理

**发现的问题**:
- `StopActiveTurns` 中 `CancelSession` 失败后仍继续执行后续步骤 — `turn.go:59-63`
  - **严重程度**: 建议
  - **修复状态**: ✅ 保持现状
  - **修复说明**: CancelSession 失败不应阻塞 DB 更新（belt-and-suspenders 策略）。日志已记录错误，后续步骤确保 turn 在 DB 层面被标记为 cancelled。这是正确的容错设计。

- Safety-net #2 中 `LoadWork` 失败时静默忽略 — `worker.go:462-480`
  - **严重程度**: 建议
  - **修复状态**: ✅ 保持现状
  - **修复说明**: 如果第二次 LoadWork 失败（Redis 暂时不可用），Pub/Sub cancel listener 仍在运行，cancel 消息仍可通过正常路径到达。这是一个合理的降级策略。

**总体评价**: 错误处理策略合理，关键路径有日志记录

### 7. 分布式系统风险

**发现的问题**:
- **[严重] Redis Pub/Sub 竞态条件** — cancel 信号在 SubscribeCancel 之前发送时丢失
  - **严重程度**: 严重
  - **修复状态**: ✅ 已修复
  - **修复说明**: 三层防护：
    1. `cancelSessionActiveScript` 持久化 cancelled 状态到 work hash（Fix 2a）
    2. Safety-net #1: LoadWork 后检查 status（Fix 2b, 覆盖窗口 1）
    3. Safety-net #2: SubscribeCancel 后重新检查 status（Fix 2c, 覆盖窗口 2）

- **[严重] StopActiveTurns 操作顺序** — DB 先于 cancel 信号更新，导致前端状态矛盾
  - **严重程度**: 严重
  - **修复状态**: ✅ 已修复
  - **修复说明**: 调换操作顺序 — 先发 cancel 信号（Fix 1），确保 worker 收到信号后再更新 DB

**总体评价**: 修复后分布式竞态风险大幅降低。Pub/Sub 的不可靠性通过 "持久化状态 + 双重检查" 的 pull 模式兜底
