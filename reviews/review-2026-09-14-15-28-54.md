### 7. 分布式系统风险

**发现的问题**:

- **[严重]** OnTurnComplete fire-and-forget goroutine 使用请求上下文 `ctx` 而非 `context.Background()` — 文件: `loop_workflow.go:152`
  - **严重程度**: 严重
  - **修复状态**: ✅ 已修复
  - **修复说明**: 注册表在调用 hook 期间持有写锁，OnTurnComplete 返回后请求上下文可能被取消。goroutine 内的 TaskScheduler.ScheduleDelayed 和 LoopRepo.Update 依赖有效的上下文。改为 `context.Background()` 并添加 panic recovery（fire-and-forget goroutine 不在任何 recover 边界内）。

- **[严重]** resumeLoopTool 缺少 active loop 检查 — 文件: `tools_loop_resume.go`
  - **严重程度**: 严重
  - **修复状态**: ✅ 已修复
  - **修复说明**: 原代码只检查了 active goal 互斥，但未检查是否已存在 active loop。如果 LLM 在同一 turn 中先调用 resume_loop 再调用 cancel_loop/complete_loop，或由于提示词歧义导致并发恢复，可能违反"每 session 仅一个 active loop"的不变量。添加了 `FindActive` 前置检查。

- **[建议]** DB.Transaction 嵌套冗余 — 文件: `loop_workflow.go:108,134`
  - **严重程度**: 建议
  - **修复状态**: ❌ 未修复（与 Goal 保持一致）
  - **修复说明**: `LoopRepo.Update` 内部已是单条 SQL（原子操作），外层 `DB.Transaction` 是冗余的。但 `GoalWorkflow.OnTurnComplete` 使用了相同模式，为保持一致性暂不修改。建议未来统一优化。

**总体评价**: 修复后良好。两个严重并发问题已修复。

### 9. 性能

**发现的问题**:

- **[建议]** resumeLoopTool 使用 `ListBySession(limit=10)` + 线性扫描查找 paused loop — 文件: `tools_loop_resume.go:48`
  - **严重程度**: 建议
  - **修复状态**: ❌ 未修复
  - **修复说明**: 当前实现取最近 10 条 loop 记录并遍历查找 paused 状态。在实践中（每 session 通常 <10 loops）不会出问题，但语义上不够精确。可考虑添加 `FindByStatus(ctx, sessionID, status)` 方法。

- **[建议]** OnTurnComplete 在注册表写锁内执行 DB 操作 — 文件: `loop_workflow.go:89-148`
  - **严重程度**: 建议
  - **修复状态**: ❌ 未修复
  - **修复说明**: 与 GoalWorkflow 行为一致（同样在锁内执行 DB 操作）。DB 操作快速（FindActive + 1-2 次 Update），不会造成锁竞争问题。

**总体评价**: 良好。无性能瓶颈。

## 遗留问题

以下为建议级未修复问题，不阻塞合并，建议后续优化：

1. **publishLoopToolMessages 与 publishGoalToolMessages 重复** — 建议提取为 `publishToolMessages` 公共函数，消除约 70 行重复代码。优先级：低。

2. **DB.Transaction 嵌套冗余** — OnTurnComplete 中的 `DB.Transaction` 包裹了已经是原子操作的 `Repo.Update`。与 Goal 模式一致，建议统一优化。优先级：低。

3. **resumeLoopTool 使用 ListBySession 查找 paused loop** — 建议添加 `FindByStatus(ctx, sessionID, status)` 方法使语义更精确。优先级：低（当前实现在正常使用场景下不会出问题）。

4. **Loop model 缺少 TokenUsage 字段** — Goal model 有 `TokenUsage int` 用于跟踪 token 消耗。Loop 可考虑在后续批次添加同等字段。优先级：低。
